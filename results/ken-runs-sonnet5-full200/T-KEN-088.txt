Not the DB — it's the application layer.

The numbers make this clear-cut:

| Metric | Value |
|---|---|
| `db_query_ms` | 12 ms |
| `app_serialize_ms` | 3800 ms |
| `rows_returned` | 50,000 |

The database returns 50,000 rows in **12ms** — that's fast, not the bottleneck. The app then spends **3.8 seconds** serializing that result set (JSON/object marshalling, likely per-row overhead like ORM hydration or reflection-based serialization) before it can respond.

So the fix belongs in the app tier, not the query:
- Serialize in bulk/streaming rather than per-row (e.g., avoid an ORM turning each row into a full object graph)
- Reduce payload size — do you actually need all 50,000 rows per response, or should this be paginated?
- Profile the serializer itself (e.g., swap a reflection-based JSON encoder for a faster one) if pagination isn't an option
