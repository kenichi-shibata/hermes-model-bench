## The real problem

The mechanism is fully understood: for both groups, the "playability vs user-data conflict" guard (`dedupe_auto.py:12-13`) matches exactly — the unplayable track holds **all** the play history, the playable track holds **none** — so the function returns `{"action": "refuse"}` both times. That is the entire reason auto-dedupe "does nothing." No crash, no matching bug.

The docstring insists this is "CORRECT safety behavior, not a bug" — but that comment papers over the actual defect: **the function conflates "which record to keep" with "which data survives."** Its `auto_merge` action only names a `keep` id and implicitly discards the loser's data. Because merging would be lossy, the guard has to refuse the single most common real-world dedupe case (dead catalog entry with history vs. live re-upload without), so the auto-canonicalizer can *never* handle these groups — every one gets kicked to a human. The refusal is a symptom; the lossy merge semantics are the disease.
