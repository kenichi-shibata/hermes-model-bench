# PR Review

## 🔴 Blocking

**`file2_pagination.py:4` — Off-by-one in offset calculation (confirmed by running it)**

```python
offset = page * limit  # BUG: should be (page - 1) * limit
```

With 1-based pages, `paginate(items, page=1, limit=5)` returns items `[6..10]` instead of `[1..5]` — the first page of results is silently dropped, and every subsequent page is shifted by one full page. Verified:

```
page=1, limit=5 -> [6, 7, 8, 9, 10]   (expected [1, 2, 3, 4, 5])
page=2, limit=5 -> [11, 12, 13, 14, 15] (expected [6, 7, 8, 9, 10])
```

Fix:
```python
offset = (page - 1) * limit
```

## 🟡 Should fix

**`file2_pagination.py` — No input validation.** After the off-by-one fix, `page=0` yields `offset = -limit`, and Python's negative slicing (`items[-limit:0]`) returns `[]` or wrong data instead of an error. Negative `page`/`limit` values produce similarly surprising results. Suggest guarding:

```python
if page < 1 or limit < 1:
    raise ValueError("page and limit must be >= 1")
```

**`file4_tests.py` — The only test is a stub.** `test_serialize` is `pass`, and there is *no test at all for `paginate`* — which is exactly where the bug lives. This PR would not have shipped broken if page 1 were asserted. Minimum coverage to add:

```python
def test_paginate_first_page():
    assert paginate(list(range(1, 21)), page=1, limit=5) == [1, 2, 3, 4, 5]

def test_paginate_second_page():
    assert paginate(list(range(1, 21)), page=2, limit=5) == [6, 7, 8, 9, 10]

def test_paginate_last_partial_page():
    assert paginate(list(range(1, 21)), page=4, limit=7) == [20]  # wait, that's wrong — see below
```

(Careful with that last one: `range(1,21)` page 4 at limit 7 → offset 21 → `[]`. A partial-page case would be e.g. 18 items, limit 7, page 3 → `[15, 16, 17, 18]`.)
