## Investigation Summary

This directory contains only 3 files — there is no actual alerting source code, config, or test suite here:

- `CONTEXT_ONLY.md` — one-line pointer explaining the other two files.
- `service_logs.txt` — 5 log lines from the service itself.
- `upstream_status_mock.json` — a single JSON record describing the payments-api dependency's status.

There is **no alert-firing code, no threshold config, no rule definitions** anywhere in this sandbox. So "fixing" an alert by editing a file is not possible here — there's nothing to patch. The task is a diagnosis/correlation exercise: cross-reference the two data files and determine whether the service's alerting behavior is consistent with reality.

## Data cross-reference

`service_logs.txt`:
```
10:00:01 INFO service healthy
10:01:01 INFO service healthy
10:02:01 INFO service healthy
10:03:01 WARN upstream dependency (payments-api) returned 503
10:04:01 INFO service healthy (own health check green)
```
Checks run every 60s. A WARN fires once at 10:03:01 for a payments-api 503.

`upstream_status_mock.json`:
```json
{"payments-api": {"status": "major_outage", "started_at": "2026-08-13T09:55:00Z", "message": "Active incident, provider-side, no ETA"}}
```
The outage started at 09:55:00 (8 min before the WARN) and has **no resolution timestamp** — it is still ongoing/unresolved as of the last log entry.

## The actual bug

The WARN at 10:03:01 is genuine and matches the mock incident (correct correlation). The problem is the very next line:

`10:04:01 INFO service healthy (own health check green)`

This log entry reverts to "healthy" one minute later with zero further mention of payments-api, even though the upstream status mock shows the outage is still `major_outage` with `no ETA` (unresolved). Two possible causes, both pointing to the same class of bug:

1. **The health/alert check doesn't re-poll the dependency every cycle** — so at 10:04 it simply didn't check payments-api again, defaulted to "healthy" based on self-status only, and the WARN condition silently cleared without confirming recovery.
2. **The overall health rollup only reflects "own" process health**, not dependency health — so a single WARN gets logged but never escalates the overall status; the moment the internal check passes, it reports "healthy" and buries the still-active dependency outage.

Either way: **the alert is broken in the sense that it does not persist/escalate for an ongoing, unresolved incident.** It fired once, then self-cleared and reported "healthy" while the real-world dependency was still in major outage with no ETA. This creates false confidence — on-call would see "healthy" in the latest log line and assume the issue is resolved, when `upstream_status_mock.json` proves it is not.

Explicitly ruled out: this is *not* a false-positive/flaky-alert problem (the WARN was accurate and well-timed relative to the real incident). It's a **missing persistence/escalation problem** — one-shot alerting that doesn't track incident state across checks.
