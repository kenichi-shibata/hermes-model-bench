## Plan for the WORK model (no files here need editing)

Since the repo only contains a static status snapshot (no app/service code), the WORK model should not attempt to "fix" anything by editing `tailscale_status_mock.json` — editing the mock would just be lying about the state, not fixing the network. Its job is to report the diagnosis and hand off the following concrete remediation steps (to be performed against the real infrastructure, outside this sandbox):

1. **Confirm `pve2` is actually down** — check power/hypervisor status of the physical/VM host at home (it's a Proxmox node based on the `pve2` hostname).
2. **Check `pve2`'s network/internet connectivity** — if the host is up but has no WAN, Tailscale can't establish a connection; check the home router's WAN link and the box's own NIC/DHCP lease.
3. **Check the Tailscale daemon on `pve2`** — `systemctl status tailscaled`, `tailscale status` locally, restart if crashed/hung (`systemctl restart tailscaled`).
4. **Verify subnet route advertisement is still enabled and approved**: on `pve2`, confirm `tailscale up --advertise-routes=192.168.1.0/24` is still part of its startup config; in the Tailscale admin console, confirm the route is still approved (not revoked) for that node.
5. **Check for key expiry** — if `pve2`'s node key expired (Tailscale defaults to periodic re-auth), it would show as offline exactly like this; re-authenticate with `tailscale up` on that node if so.
6. **Once `pve2` is back online**, re-run `tailscale status --json` and confirm `Peer.home-router-node.Online == true` and the route is present — then retest reachability to `192.168.1.x` from the phone.

No file changes in this sandbox are required or appropriate; the actionable fix is entirely on the `pve2` host/Tailscale admin side.
