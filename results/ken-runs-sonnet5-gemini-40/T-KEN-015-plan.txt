## The real problem

The comment ("this is CORRECT safety behavior, not a bug") is misleading in context. It's true that *blindly deleting the record with play history* would be a data-loss bug, and refusing to do that blindly is reasonable. But the check as written treats "which copy to keep" and "what to do with the play_count" as one indivisible decision — and only offers two outcomes: fully auto-merge (dropping the data) or fully refuse (merging nothing). It never considers the obvious third option: **keep the playable copy, but carry the play_count forward onto it.**

That's why "auto dedupe isn't doing anything" for these two groups: the only two real duplicate groups in the dataset are precisely the case the tool is hard-coded to always refuse — a case where the correct survivor is *not actually ambiguous* (the playable one), only the metadata handling is unresolved. So the "safety" branch isn't protecting against genuine ambiguity here; it's blocking a resolvable case because the code has no representation for "merge + carry forward user data."
