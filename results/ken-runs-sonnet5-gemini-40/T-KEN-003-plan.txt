## Investigation Summary

**Files examined:**
- `performers.json` — `{"performers": [...]}`, 2700 records, each `{id, name, image, stashdb_id}`
- `stashdb_mock.py` — one function: `get_fallback_image(stashdb_id)` → `https://stashdb.org/images/{stashdb_id}.jpg` (or `None` if `stashdb_id is None`)

**Root cause found:**
All `image` URLs follow the pattern `http://<host>:9999/performer/<id>/image`, but there are **two different hosts** in the data:

| Host | Count | ids |
|---|---|---|
| `198.51.100.69:9999` (current/working) | 2521 | 179–2699 |
| `198.51.100.64:9999` (broken/decommissioned) | **179** | 0–178 |

That's the "179 broken images" — an exact match to the bug report. These are the oldest performer records (id 0–178), still pointing at an old/dead image host that was apparently replaced by `.69` at some point.

**Not all 179 are fixable the same way**, because of a second detail in the data:
- Of the 179 broken records, only **ids 0–39 (40 records)** have a non-null `stashdb_id` (e.g. `"stashdb-0"`).
- **ids 40–178 (139 records)** have `"stashdb_id": null` — there is no lookup key for them, so `stashdb_mock.get_fallback_image()` returns `None` for them. There is no data anywhere in this sandbox that gives a real image for these 139.

So the honest fix has two parts, not one blanket find/replace:

1. **179 broken records total**, split into:
   - **40 records (id 0–39)** — have a `stashdb_id` → get a real replacement URL via `stashdb_mock.get_fallback_image(stashdb_id)`.
   - **139 records (id 40–178)** — no `stashdb_id`, no fallback source exists → cannot be pointed at a real image. Must be handled as "no image available" (e.g. `image: null` so the frontend renders its default placeholder), not silently left pointing at a dead host.

Just rewriting host `.64` → `.69` for all 179 would be the wrong fix: those 139 performers were never migrated to the `.69` server (no evidence they exist there), so faking that host would just trade one broken URL for another likely-404 URL. The `stashdb_id`/`stashdb_mock` presence is the deliberate signal for which subset actually has a legitimate source of truth to fix from.

## Exact steps for the WORK model

1. **Do not** do a blind string-replace of `198.51.100.64` → `198.51.100.69` across the file — verify first (per above) that this is not actually correct for the 139 ids lacking `stashdb_id`.

2. Write a small script (e.g. `fix_performer_images.py`, one-off, can be deleted after running — or just do it inline) that:
   ```python
   import json
   from stashdb_mock import get_fallback_image

   with open("performers.json") as f:
       data = json.load(f)

   fixed, unresolved = 0, []
   for p in data["performers"]:
       if "198.51.100.64:9999" in p["image"]:
           fallback = get_fallback_image(p["stashdb_id"])
           if fallback:
               p["image"] = fallback
               fixed += 1
           else:
               p["image"] = None      # no source of truth for a real image
               unresolved.append(p["id"])

   with open("performers.json", "w") as f:
       json.dump(data, f, separators=(", ", ": "))  # match existing compact, non-indented style

   print(f"fixed={fixed} unresolved={len(unresolved)}")
   print("unresolved ids:", unresolved)
   ```
   Note: keep the JSON output style consistent with the current file (it's currently written compact/non-pretty with `", "`/`": "` separators, single line, no trailing newline needed) so the diff stays minimal and doesn't reformat unrelated records.

   - 139 records (id 40–178) get `image: null`.
